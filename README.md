# procko.pro — Tyler T. Procko, Ph.D.

Personal portfolio and CV site for [Tyler T. Procko](https://procko.pro) — AI/Knowledge Graph Engineer, Ontologist, DoD-cleared.

## Architecture

Personal content lives in **`public/data/tyler-procko.yaml`**. The shared term catalog, **`src/data/competencies.json`**, defines competency identities, labels, categories, and aliases.

```
public/data/tyler-procko.yaml   ← single source of truth for all CV/portfolio content
│
├── .github/
│   ├── workflows/
│   │   ├── deploy.yml                        ← build + deploy to GitHub Pages on push to main
│   │   ├── sync-repo-descriptions.yml        ← daily sync of GitHub repository identities, URLs, and descriptions
│   │   ├── discover-new-repos.yml            ← daily discovery; avoids duplicate open PRs and cleans closed branches
│   │   ├── sync-openalex-publications.yml    ← weekly sync of new publications from OpenAlex
│   │   └── check-links.yml                   ← weekly link check
│   └── scripts/
│       ├── sync_openalex_publications.py     ← queries OpenAlex by ORCID; deduplicates, updates citation counts, adds stubs
│       ├── discover_new_repos.py             ← finds public repos and infers technologies/domains from metadata
│       └── sync_repo_descriptions.py         ← syncs repository metadata from GitHub
│
├── build.py                    ← Python/Jinja2 builder → public/legacy/cv.html
│   templates/                  ← Jinja2 partials (one per section)
│
├── public/
│   ├── legacy/cv.html          ← legacy HTML CV (generated by build.py, served at /legacy)
│   ├── data/tyler-procko.yaml  ← personal content fetched by the React app at runtime
│   ├── CNAME                   ← custom domain (procko.pro)
│   └── 404.html                ← SPA routing redirect for GitHub Pages
│
└── src/
    ├── data/competencies.json  ← shared catalog bundled by Vite and read by Python
    ├── lib/
    │   ├── yaml-loader.ts      ← fetches + validates YAML at runtime (Zod)
    │   ├── schema.ts           ← Zod schema matching the YAML structure
    │   ├── cv-data.ts          ← transforms Person → renderer-agnostic CVData/ResumeData models
    │   ├── graph-builder.ts    ← builds Cytoscape node/edge graph from Person data
    │   ├── competencies.ts     ← resolves identities and aggregates supporting records
    │   ├── tech-categories.ts  ← category menu data derived from the shared catalog
    │   └── ui-constants.ts     ← shared Tailwind class tokens for consistent sizing
    ├── components/
    │   ├── SiteFooter.tsx
    │   └── SEO.tsx
    └── pages/
        ├── Landing.tsx         ← boot-sequence animation, skills matrix, publications, projects
        ├── About.tsx           ← extended bio and personal info
        ├── CVExport.tsx        ← full CV as downloadable PDF + HTML preview (/cv)
        ├── ResumeExport.tsx    ← condensed resume as downloadable PDF + HTML preview (/resume)
        └── Graph.tsx           ← interactive knowledge graph via Cytoscape (/graph)
```

## Routes

| Route | Description |
|-------|-------------|
| `/` | Landing — terminal boot animation, ranked skills matrix, publications, projects |
| `/about` | Extended bio, education, awards, links |
| `/cv` | Full CV — all publications grouped by status, all experience, downloadable PDF |
| `/resume` | Condensed resume — featured work, projects, skills, downloadable PDF |
| `/graph` | Interactive knowledge graph of skills, publications, projects, and experience |
| `/projects` | Searchable project directory with domain filtering and date/name sorting |
| `/projects/:slug` | Source-driven detail page for every visible project |
| `/papers` | Publication directory with search, year/classification filters, and date/name sorting |
| `/personal` | Drawing gallery with a lightbox |
| `/legacy` | Generated legacy CV |

Static public routes are listed in `public/sitemap.xml` and rendered to HTML by `npm run prerender` after the build. Project detail routes are expanded directly from visible YAML project records by `scripts/project-routes.mjs`, then added to the generated sitemap. Project snapshots wait for their content and canonical URL to be ready instead of a fixed delay per record. When adding a static route in `src/App.tsx`, also update the sitemap, the route list in `scripts/prerender.mjs`, and `PAGE_INPUTS` in `scripts/page-updates.mjs`. Tests cover static routes and agreement between generated project URLs and browser links.

The project directory includes every project without `graph_exclude: true`, independently of CV exclusions. Each detail page uses the existing title, tagline, description, year, links, and canonical competency labels. Its URL defaults to the stable project ID without the leading namespace. An optional `page` object in the same YAML record adds `slug`, `sections` (each with `heading` and `paragraphs`), resource `links` (`label`, `url`), and an `image` (`src`, `alt`, optional `caption`). Source slugs must be unique, including collisions with default URLs. The first four expanded write-ups summarize their project READMEs; the OCSF screenshot comes from that repository. These additions are editorial source content, not browser requests to GitHub.

The interface uses square controls and chips. Shared `chamfer-card`, `chamfer-frame`, and `chamfer-action` styles in `src/index.css` add selective 45-degree corners to major surfaces and primary actions; chamfered buttons keep keyboard focus indicators inside the cut boundary. The avatar displays a centered 15% crop from each side of the source photo at 144px tall on desktop and 96px on small/landscape-phone screens. Its top-right and bottom-left chamfers stay separate from the scan-reveal animation and falling-code effect. Skill chips use the shared `chamfer-chip` style with top-left and bottom-right cuts, including ranked/category views, repository tags, overflow menus, and project details.

The homepage competency and repository grids cover the full section width; their content stays inside the shared centered width limit.

Project pages are lazy-loaded. The homepage offers “View all projects” and “View on GitHub” beneath recent projects; the top navigation is unchanged. Project and competency links open their graph connections, with record IDs surviving title changes. Search, domain filtering, and date/name sorting operate on the loaded YAML; newest project dates are shown first by default, with undated records last in either date order. The six recent homepage previews retain their GitHub activity dates, and their titles and “View project” links open the corresponding local detail pages. If the GitHub feed fails or produces no matching records, the previews fall back to six source projects and label their YAML dates as “project date”; they do not invent GitHub creation or update timestamps. Unavailable/hidden project routes show a noindex not-found page. To review locally, run `npm run dev -- --host 127.0.0.1` and open `/projects`; `node scripts/test-project-pages.mjs` checks every visible detail page, sorting, filtering, the six homepage preview links, hidden records, and mobile overflow. Project detail update dates track their own source record and image rather than every project in the YAML; shared component changes still affect all consuming pages.

The publications directory at `/papers` uses the same source visibility rule as the homepage: omit `in_progress` entries and retain other classifications as labeled. It shows source authors, venue, date, author role, optional abstract, reading links, and graph connections. The homepage keeps its recent-publication previews and puts “View all publications” to the left of “View on Google Scholar”; the Scholar destination comes from `social_links` in the YAML. The directory is lazy-loaded, included in the sitemap, and tracks meaningful source updates from the publications section. Individual paper detail pages are a subsequent step. Run `node scripts/test-publication-pages.mjs` against the local dev server to check both buttons, source coverage, filtering, sorting, direct loading, and mobile layout.

Prerendering fills `dist/sitemap.xml` with per-page UTC update timestamps recovered from the checked-out commit's first-parent Git history. `PAGE_INPUTS` identifies each page's entry module, consumed YAML sections, and public assets. Local imports are followed automatically; shared layout, styles, metadata, profile fields, and package manifests affect all consuming pages. YAML key order, formatting, and comments do not change the fingerprint. README/test/workflow changes, build times, generated bundle names, and live activity widgets do not reset dates. A rebuild of the same source preserves them. This is conservative source-change tracking: any code edit or edit within a consumed YAML section counts, even if its visible effect is small. Update the field/asset rules when a page starts consuming new data or assets. Local dates describe committed source, not uncommitted edits.

The deployment checkout includes complete commit/tree history with `filter: blob:none` so old image binaries are not fetched for date tracking. Missing history or route rules fail the build rather than inventing dates. No cache, bot commit, or separate scheduled job is required. The initial backfill resolves all seven pages to `8a2f786` (2026-11-20 17:17:10 UTC), which corrected their shared search/sharing metadata. Tests use temporary repositories to cover unrelated changes, imported modules, YAML edits, assets, merges, and shallow-history rejection. `scripts/test-seo.mjs` also checks the delivered sitemap and profile timestamps.

`SEO.tsx` owns each route's title, description, robots directive, canonical URL, and Open Graph/Twitter title and description. The HTML shell retains shared image metadata but does not duplicate route-specific tags. Every page supplies its metadata explicitly; the homepage uses the YAML name, headline, SEO description (or summary), and its existing publication count. Prerendering includes these tags in the delivered HTML. After building and prerendering, start the preview server and run `node scripts/test-seo.mjs` to check every generated page with JavaScript disabled, then compare metadata during client navigation. `SITE_URL` overrides the preview server address. Unit tests cover tag ownership and sharing consistency.

The graph, CV, and résumé pages load through `React.lazy` when their routes are opened, keeping Cytoscape and the PDF renderer out of the initial homepage download. Navigation remains available during the loading state. PDF generation still starts when a document page opens. Unit tests check deferred module loading. After building and prerendering, run `npm run preview -- --host 127.0.0.1`, then `node scripts/test-route-loading.mjs` to check the homepage's JavaScript budget, navigation, direct links, PDF bytes, and PDF/HTML toggles. `SITE_URL` overrides the preview server address.

Internal page navigation uses a 900 ms terminal transition in `PageTransition`, typing `cd ~/destination` within the content viewport while leaving the header and any visible footer unobscured. It skips initial loads, same-path/query changes, and reduced-motion preferences. The destination mounts after the terminal clears; there is no visible generic loading-page text. Footer links use the router, and rapid navigation cancels pending swaps. Run `node scripts/test-page-transition.mjs` against the dev server (`SITE_URL` overrides it) to check navigation, header/footer boundaries, reduced motion, and graph mounting after the transition under CPU throttling.

Graph layout runs in a dedicated Web Worker using the existing fCoSE engine. Node dimensions are measured in the visible renderer and sent to the worker; only final positions return to the UI. Leaving the graph unmounts it immediately, aborts pending data requests, and terminates any layout worker, including Reset Layout work. Completed layouts remain cached locally. `node scripts/test-graph-cancellation.mjs` verifies cancellation during calculation, successful reentry, and Reset Layout cancellation; unit tests cover worker results/errors and aborted data loading.

## Updating content

The social-sharing card lives at `public/og-image.png`. When replacing it, update the image dimensions and alternative text in `index.html`. `npm test` checks that Open Graph and Twitter reference the same PNG and that its dimensions match the metadata.

Structured profile metadata is populated from YAML during `npm run prerender`. `primary_work_experience` selects the current work record whose `organization` and optional `org_url` identify the employer; it must have `is_current: true` and no end date. This explicit reference avoids guessing among consulting roles. The profile name, headline (the part of `title` before ` — `), summary, email, website, social links, and ORCID also come from YAML. The shared ProfilePage entity identifies the homepage, so its modification time uses the homepage's recovered source update date on every route. These fields are absent from the `index.html` template and filled into every generated page; local development without prerendering has only the static metadata template. Tests check employer changes and reject missing or ended primary work records.

For personal content, edit `public/data/tyler-procko.yaml`. The React app fetches it at runtime — no rebuild needed for content changes. The legacy HTML view requires `python3 build.py` to regenerate.

New publications are synced automatically every Monday via the OpenAlex workflow. Stubs are tagged `source: openalex` and `featured: false` for manual review.

Certificate `resume_exclude` is an optional boolean validated by `CertificateSchema`. Parsing preserves it so excluded certificates stay off the résumé; tests check the actual portfolio through parsing and résumé generation.

Every social link requires a stable, unique `id`. Personal links use `social/<platform>`; associate links use `social/<associate-slug>/<platform>`. IDs are internal identifiers, separate from display labels and URLs. The portfolio schema test validates the complete YAML and checks social-link IDs for missing, empty, or duplicate values during `npm test`, including deployment builds.

The browser loader rejects malformed YAML and data that fails `PersonSchema`, displays a readable error through each page's error state, and logs diagnostic details in the browser console. Only validated data is cached; failed loads can be retried. Loader tests cover rejection, recovery, and caching. With the dev server running, `node scripts/test-portfolio-errors.mjs` checks error screens on the homepage, About, graph, CV, and résumé, plus a valid homepage load. Set `SITE_URL` to check another server; invalid responses are simulated inside the test browser only.

Publication `status` values are validated by `PublicationSchema` in `src/lib/schema.ts`: `published`, `awaiting_publication`, `in_progress`, `colleague_thesis`, `competition_proposal`, `grant_proposal`, and `article`. The latter four preserve existing portfolio classifications also used by the legacy CV. Unknown values are rejected by the schema.

### Graph hit detection patch

Graph selection regression tests also require Cytoscape initialization and selection to produce no warnings. Unsupported shadow declarations were removed; Person labels and selected-node borders retain their existing styling.

Graph DOI buttons normalize both bare identifiers and full DOI resolver URLs into one HTTPS resolver URL. Selection tests prevent duplicated resolver prefixes. See the [current link audit](docs/current-link-audit.md) for source-URL checks and publisher access limitations.

Cytoscape is pinned to 3.33.1 with `patches/cytoscape+3.33.1.patch`. Its polygon hit test counted a shared vertex twice, causing clicks and taps along a diamond's center axis to miss. The patch uses a half-open edge interval to count that vertex once, preserving node shapes. It covers the dependency source and the ESM/CommonJS bundles used by this project. `postinstall` applies it through `patch-package --error-on-fail`; a failed patch blocks installation instead of silently losing the fix.

`npm test` covers polygon interiors, exteriors, vertex order, translation, and scaling. Run `node scripts/test-graph-hit-detection.mjs` against the dev server (or set `SITE_URL`) for real mouse/touch selection of Person and Associate diamonds at three zoom levels. Before upgrading Cytoscape, check the upstream implementation and rerun these tests; remove the patch and its install tooling once an upstream release passes them without it.

## Maintaining competencies

Skill chips are native graph links with keyboard focus indicators. Graph type filters show focus on the whole label and toggle with Space. Search lists matching nodes across all types, including hidden ones: Tab reaches each result, Down enters the list, Enter in the field selects the first result, and Escape clears the query and returns focus to the field. Selecting a result reveals that node and uses the existing details/neighbor-selection behavior. The result list scrolls within the controls panel.

Navigation text uses theme colors checked against a minimum 4.5:1 contrast ratio. Run `node scripts/test-accessibility.mjs` against the dev server (or set `SITE_URL`) to check skill-link activation, navigation contrast, graph-filter focus, hidden-node search selection, and empty results in both themes, with desktop/mobile graph layouts. This is targeted regression coverage, not a full accessibility certification.

Add a new term once in `src/data/competencies.json`, then reference it from a portfolio record. Each term has a permanent lowercase `id` (letters/numbers separated by single hyphens), a display `label`, a `category` from the same catalog, and an `aliases` list. IDs, labels, and aliases are accepted in record fields; matching ignores case and surrounding whitespace. Keep the ID unchanged when renaming a label, and add the previous label as an alias if records still use it. Catalog changes require a rebuild.

Homepage chips, project tags, the graph, and React CV/resume skills resolve through `src/lib/competencies.ts`. Category comes from the catalog, not the YAML field. Graph links use stable IDs (`/graph?term=sparql`); free-text `?q=` links also resolve catalog references. Aliases never create additional nodes or counts. Graph links and connected-node navigation reuse the node-click handler, so the selected details, neighbor expansion, and neighborhood dimming stay consistent. On mobile, the type filters have bordered, clickable arrow buttons and edge fades. Arrows disable at the ends; the row also supports swiping and keyboard scrolling. Hidden checkbox inputs stay inside this scroll area so they cannot widen the details drawer.

The graph fills the space below the navigation bar, keeping its mobile controls on-screen. The complete drawer opens and closes with a 220 ms ease-in-out slide/fade; reduced-motion preferences disable the transition, and closed controls cannot receive focus. Verify this with `node scripts/test-graph-drawer-motion.mjs` against the dev server (or set `SITE_URL`). Selecting a node opens the mobile drawer with details and connections first. Connection rows use compact padding and wrap longer labels without a fixed minimum height. Connections start with five entries; “Show N more” expands the list and “Show fewer” collapses it. Selecting another node resets the preview. The details drawer scrolls vertically only, with gradient “More above/below” buttons where additional content remains. Resize observers track expanding content and viewport changes. Run `node scripts/test-graph-mobile.mjs` against `npm run dev` to check viewport bounds and canvas/connection clicks; set `MOBILE_TOUCH=1` for consistent phone emulation and touch input (including a short press duration), or `SITE_URL` for another host.

Counts mean distinct supporting records across education, work, publications, projects, courses, certificates, talks, and extracurriculars. A repeated competency within a record counts once. All views use the graph's existing evidence policy: omit `graph_exclude` work/projects and deprecated certificates. Presentation filters remain intentional: ranked chips hide office/communication tools; CV/resume hides OS/personal/domains and shows at most 20 skills per category. The legacy HTML's manually curated skills list is separate from these evidence counts. For projects, `graph_exclude` controls site/graph visibility, while `cv_exclude` independently excludes the project from both CV and resume. Personal & Creative Work stays visible on the site with 19 tools under Personal & Creative Use, but remains excluded from document exports. Telegram is a Communication Tool attached only to the Christian Denominations Wikidata project; the five other previously excluded projects remain hidden with explicit `graph_exclude` flags.

Validation rejects unknown references, duplicate references within a field, duplicate IDs, invalid categories, and ambiguous names/aliases. Field/category disagreements are reported for review; the catalog still determines rendering. Tests compare all real-data competency counts with their graph evidence links. See [classification review](docs/competency-review.md) for unresolved editorial decisions.

## Deployment

Pushes to `main` trigger `.github/workflows/deploy.yml`, which:
1. Runs `build.py` to regenerate the legacy HTML from YAML
2. Runs `npm run build` to produce the Vite `dist/`
3. Deploys `dist/` to GitHub Pages at `procko.pro`

The daily repository metadata sync uses `AUTOMATION_TOKEN` to open an auto-merge PR after validating updated references. Required PR checks run before merging; the merge to `main` triggers deployment. Unchanged metadata creates no commit or PR. If metadata changes but the token is missing, the job fails explicitly instead of publishing an update that cannot trigger validation. The token needs Contents and Pull requests write permissions, as used by the publication-sync workflow. Sync runs are serialized and only publish from `main`.

Tracked GitHub repositories carry a numeric `github_repo_id` in the source YAML. The daily sync resolves existing IDs through `GET /repositories/{id}`; records without an ID are resolved by their repository URL on first sync. It updates canonical repository links and nonempty About descriptions, while preserving portfolio IDs, authored titles, project-page slugs, and distinct project websites. Repository-level extracurricular links carry the same identity metadata so discovery does not import them as new projects. Links to individual issues or pull requests stay untouched.

Discovery reconciles tracked repositories before comparing IDs, independently of whether the earlier sync has merged. A rename or transfer updates the existing record. A different repository reusing an old name gets a new record; a conflicting portfolio address receives a repository-ID suffix. Topic validation distinguishes a rename from an actual addition. Homepage previews also match IDs, keeping their local detail links available before a URL correction has merged.

An unavailable, private, or mismatched repository aborts reconciliation before writing the YAML; failed repository listings also abort discovery. This avoids guessing identity or importing private metadata, but a deleted repository needs manual attention before these jobs can resume. On initial ID backfill, a URL alone cannot identify an original repository if its former name has already been reused ([GitHub rename behavior](https://docs.github.com/en/repositories/creating-and-managing-repositories/renaming-a-repository)). Once stored, IDs are authoritative; there is no fallback to a potentially reused URL.

Repository identity regressions run in discovery, metadata sync, PR validation, and deployment using the standard Python test runner:

```bash
python3 -m unittest discover -s tests -p test_repository_identity.py
```

Workflow regression checks:

```bash
python3 -m pytest tests/test_description_sync_workflow.py -q
```
